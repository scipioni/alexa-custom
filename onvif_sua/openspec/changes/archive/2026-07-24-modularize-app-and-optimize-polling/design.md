## Context

The whole service lives in a single 3167-line `app.py`: config/env parsing (`_load_settings_yaml`, `_get_cred_fallbacks`, `SETTINGS_FILE`), MQTT discovery/publish (`_mqtt_*`), ONVIF connect/services/close (`_try_connect`, `_get_services`, `_safe_close`, `_safe_unsubscribe`), subnet scanning (`_probe_ip`, `_subnet_scan_once`, `_tcp_probe`), the Dahua CGI + keepalive threads, the FastAPI app with ~20 `/api/*` routes and session/HMAC auth, and three large HTML/CSS/JS blobs built by `_html_login()`, `_html_settings()`, `_html()`. It is deployed via `docker-compose.yml`, which bind-mounts `./app.py:/app/app.py:ro` and runs the module directly.

Two external contracts must not change: (1) the MQTT topic/payload schema Home Assistant consumes, and (2) the web dashboard's endpoints and rendered DOM. The refactor is structural; the two polling tweaks are the only intentional behavior changes, and they are client-side only.

## Goals / Non-Goals

**Goals:**
- Reorganize `app.py` into the `onvif_sua/` package described in the proposal, one concern per module.
- Preserve MQTT output (topics, unique_ids, discovery + state payloads) exactly.
- Preserve every HTTP route path, method, request/response shape, and the rendered GUI.
- Extract inline HTML/CSS/JS into `web/templates/` (Jinja2) and `web/static/` without changing what the browser receives (beyond the polling changes).
- Slow dashboard polling (`refresh` 4s→15s, `refreshAlarms` 3s→12s) and pause it when the tab is hidden.
- Make the package installable via `pyproject.toml` (Python 3.13) with a console entrypoint, runnable both natively (`pip install .` → `onvif-sua`) and via Docker, from one shared entrypoint.

**Non-Goals:**
- No change to MQTT semantics, ONVIF/Dahua protocol handling, alarm logic, or the persisted `events.json`/`alarm.json` formats.
- No new features or endpoints. One new config key is added deliberately: `web.asset_version` in `settings.yaml`, used solely as the static-asset cache-busting token (see the cache-revalidation decision); no other config keys change.
- No test framework introduction beyond what's needed to assert behavior preservation (optional).
- No change to the server-side event/heartbeat/rule-check cadences (those are MQTT/liveness paths, not the web polling path).

## Decisions

### Decision: Package layout mirrors the proposal, imports flow one direction
Modules layer as: `config` (leaf) → `mqtt`, `connect`, `scan` → `web/`. The ONVIF connection code is a plain `onvif_sua/connect.py` module at the package root, **not** an `onvif_sua/onvif/` subpackage (RL1): naming an internal package `onvif` would shadow — and is easy to accidentally resolve instead of — the third-party `onvif` library, which the code locates on disk via `__import__("onvif").__file__` to find its bundled WSDL directory. A neutral module name removes that footgun at no cost; do not reintroduce an `onvif/` subfolder. `__main__.py` is the only place wiring them together and holding the `if __name__` startup sequence (`_load_settings_yaml`, `_load_alarm_file`, `_mqtt_init`, web thread, save thread, `asyncio.run(_main_loop_coro())`). Shared mutable runtime state (the camera registry, `_active_pullpoints`, alarm state) currently lives as module-level globals in `app.py`; to avoid circular imports it moves to a small `state.py`-style home imported by the others (decided during implementation — either a dedicated `state` module or kept in `config`). **Alternative considered:** passing state via a context object/DI — rejected as over-engineering for a behavior-preserving refactor; keep the global-registry pattern that already works.

### Decision: Templates extracted verbatim into Jinja2, then modified only for polling
`_html_login()`, `_html_settings()`, `_html()` become `login.html`, `settings.html`, `index.html`. The extraction is mechanical: move the string content into template files, convert the existing Python f-string interpolations into Jinja2 variables, and serve via `Jinja2Templates`. To guarantee equivalence, capture deterministic baselines before the move and diff against the post-move render (see task 1.1 for the harness). The `_html_*()` builders return static raw strings — no server-side data interpolation, all dynamic data loads client-side via `/api/*` — so page HTML is deterministic by construction; capture the exact bytes via FastAPI `TestClient` with a fixed session and a committed fixed `settings.yaml`. Note the page HTML is NOT byte-identical after extraction (an inline block becomes an external `<link>`/`<script src="...?v=...">` reference), so parity is checked two ways: each extracted `static/*` file is byte-identical to the inline block it came from, and the page HTML matches the baseline except for each moved block being replaced by its asset reference. Only after parity is confirmed do we apply the two polling edits to `index.js`. **Alternative considered:** leave templates as Python strings in a `templates.py` module — simpler but keeps a 500+ line blob and misses the stated goal of real template/static files.

### Decision: CSS/JS split into per-page static files served by FastAPI `StaticFiles`
Each page owns its own CSS and JS. `_html_login()`, `_html_settings()`, `_html()` each carry a distinct `<style>` and `<script>` block, so they extract to **three pairs**: `web/static/login.css`+`login.js`, `settings.css`+`settings.js`, `index.css`+`index.js`. Each template references only its own pair. Mount `StaticFiles` at a fixed path. The polling constants live in the dashboard's `index.js`, so the two behavior changes are localized to `index.js`.

**They are deliberately NOT merged into one shared `app.css`/`app.js`.** Verified against `app.py`: the three pages share no JavaScript — `apiFetch` and the pollers (`refresh`/`refreshAlarms`/`setInterval`) are defined only in the dashboard block; login and settings use plain `fetch` and have zero function-name overlap with each other or the dashboard. A single shared `index.js` loaded on `/login` would run the dashboard pollers against DOM ids (`subnet-badge`, `alarms-card`, …) that don't exist there — throwing runtime errors and firing stray `/api/*` polling from the unauthenticated login screen. Because that failure is runtime-only, the render/DOM diff (below) would NOT catch it; per-page files remove the failure mode structurally and also keep the extraction a verbatim block-for-file move (no merging → no CSS-rule bleed between pages either). **Alternative considered:** one shared `app.js`/`app.css` — rejected for the cross-page-execution and CSS-bleed reasons above; there is no shared code to justify it. **Alternative considered:** a `common.js` for shared helpers — rejected because nothing is actually shared, so it would be empty. **Alternative considered:** inline the CSS/JS in the templates — avoids a static mount but keeps the files huge and defeats the extraction goal.

Three concerns are pinned down here so extraction can't quietly break deployment:
- **Directory resolution (RM1):** `StaticFiles(directory=...)` and `Jinja2Templates(directory=...)` resolve their paths from the package location — `Path(__file__).resolve().parent / "web" / "static"` and `.../ "web" / "templates"` (or `importlib.resources.files("onvif_sua.web")`), never CWD-relative. `web/templates/` and `web/static/` are declared as package data via the setuptools `[tool.setuptools.package-data]` block above (`"onvif_sua" = ["web/templates/*.html", "web/static/*"]`) so they ship with the install. This must hold for a non-editable `uv pip install .` with no source bind-mount, not just for editable/bind-mounted layouts — otherwise a real install serves 500/`TemplateNotFound`. **Alternative considered:** CWD-relative paths — works only when launched from the repo root or under a bind mount, so rejected.
- **Auth exposure (RM3):** the `/static` mount is not gated by the per-route `_valid_session` check. Note `_valid_session` is a plain helper called manually at the top of each protected route (`if not _valid_session(request): return 401/redirect`), not a FastAPI `Depends(...)` dependency; a `StaticFiles` mount is a separate sub-app that is unauthenticated by default, so there is nothing to remove — the mount is simply left ungated. The extracted assets contain no secrets, and the login page is not session-gated and needs its stylesheet — gating `/static` would 302-redirect the login CSS to `/login` and leave the form unstyled. The (minor) trade-off is that the dashboard JS, previously embedded only in an authenticated page, becomes fetchable unauthenticated; accepted since it exposes no data. For completeness, note that the alarm-data endpoints `/api/alarms` and `/alarm.json` are **already unauthenticated in the pre-refactor `app.py`** (they have no `_valid_session` check) and remain so — this is behavior-preserving and out of scope to change here; it is documented so the pre-existing exposure is a known, accepted fact rather than a surprise introduced by the refactor.
- **Cache revalidation (RL2, RM1):** externalizing JS/CSS introduces browser caching, so a long-lived kiosk could keep serving an old `index.js` after a future polling-constant edit. The cache-busting version token is **sourced from `settings.yaml`**: a `web.asset_version` string key is loaded by `config.py` into the runtime config (default `"1"` when absent), exposed to the templates as a Jinja2 global `asset_version`, and every `/static/*` reference carries `?v={{ asset_version }}` (e.g. `/static/index.js?v={{ asset_version }}`). To push edited assets to kiosks, an operator bumps `web.asset_version` in `settings.yaml` and restarts — every asset URL changes, forcing a re-fetch. The settings load/save path must round-trip `web.asset_version` so the GUI's `_save_settings_yaml()` does not drop it. `settings.yaml.example` documents the key. **Why `settings.yaml` rather than package version / git SHA:** the operator already edits `settings.yaml` per deployment and it is the mounted, authoritative config surface; a value there is explicit and requires no build-time injection or metadata lookup. `StaticFiles` `Last-Modified`/`ETag` revalidation MAY additionally apply but is not the primary mechanism. **Alternatives considered:** `importlib.metadata.version()` or a build-time git-SHA env var — rejected: they require a rebuild/reinstall to change and don't fit the "edit config + restart" operator workflow the bind-mount enables; **no versioning** — rejected because edits would silently not reach kiosks until a manual hard reload.

### Decision: Polling — constants + visibility handler
In `index.js`:
- `setInterval(refresh, 4000)` → `15000`; `setInterval(refreshAlarms, 3000)` → `12000` (values within the proposal's ranges).
- Reuse the existing `paused` guard: add a `visibilitychange` listener that sets an "auto-paused" flag from `document.hidden` and, on becoming visible, immediately calls `refresh()` + `refreshAlarms()` so the panel is current without waiting a full interval. Keep the manual `⏸ Pausa` button independent so auto-pause doesn't fight the user toggle. **Alternative considered:** `clearInterval`/`setInterval` teardown on visibility change — functionally equivalent but the guard-flag approach is a smaller diff over the existing `if(paused) return;`.

### Decision: `pyproject.toml` is the single packaging source; one entrypoint, two run modes
Add a `pyproject.toml` targeting Python 3.13 (`requires-python = ">=3.13"`) with **setuptools** as the build backend (chosen over hatchling — most widely understood here, and its package-data declaration is well-known; the backend is pinned so the template/static inclusion mechanism is unambiguous, per RM3), the dependencies currently in `requirements.txt` (fastapi, uvicorn, onvif-zeep-async, requests, paho-mqtt, PyYAML), and a `[project.scripts]` console entry `onvif-sua = "onvif_sua.__main__:main"`. The concrete build config is:

```toml
[build-system]
requires = ["setuptools>=68"]
build-backend = "setuptools.build_meta"

[tool.setuptools.packages.find]
include = ["onvif_sua*"]

[tool.setuptools.package-data]
"onvif_sua" = ["web/templates/*.html", "web/static/*"]
```

The explicit `[tool.setuptools.package-data]` globs are what guarantee the extracted templates and static assets are copied into the built wheel (Python otherwise ships only `.py` files); this does not depend on a `MANIFEST.in` or VCS state. **Alternative considered:** hatchling with `[tool.hatch.build.targets.wheel] force-include`/`artifacts` — rejected only to remove the "setuptools or hatchling" ambiguity, not on merit. The startup sequence lives in a `main()` function so it is callable identically by the console script, by `python -m onvif_sua`, and by an in-process import. Both run modes use this one entrypoint — no duplicated boot logic, **and both install with the same single verb, `uv sync --frozen`** (see the lockfile decision below), so there is exactly one native/Docker install path and no divergence:
- **Native:** managed with [uv](https://docs.astral.sh/uv/). Create the venv with `uv venv --python 3.13` (uv fetches 3.13 if absent), then `uv sync --frozen`, and run via `uv run onvif-sua` / `uv run python -m onvif_sua` — no manual `source .venv/bin/activate` needed (uv auto-uses `.venv`). Installing into the uv-managed venv is the expected native workflow — no system/global installs. **Note:** `uv sync` installs the project itself in **editable** mode by default, so the venv imports `onvif_sua` from the source tree; this is the same mechanism that lets the Docker bind-mount work without a rebuild (below). `uv pip install -e .` / `uv pip install .` are NOT used as the run/setup verb anywhere (a plain non-editable `uv pip install .` is used only in a one-off packaging test — see task 4.5 — to prove the built wheel ships templates/static as package data; it is a validation step, not a run mode).
- **Docker:** the image runs `uv sync --frozen` (same verb, editable project + frozen deps) and its `CMD` invokes the same `onvif-sua` via `uv run`.
`requirements.txt` stops being the source of truth. **Alternative considered:** keep `requirements.txt` + `python app.py` and skip packaging — rejected, the user explicitly wants an installable Python 3.13 package alongside Docker.

### Decision: A committed `uv.lock` is the reproducibility source of truth for both modes
`pyproject.toml` declares dependency **ranges** (maintained intent), but ranges alone don't guarantee the two run modes get the same versions: "both install from `pyproject.toml`" still lets the native venv and the Docker image *re-resolve independently at different times* and land on different versions (e.g. a cached image on `fastapi 0.110` vs. a fresh `uv pip install` pulling `0.120`). That silently breaks the "identical runtime behavior" invariant between native and Docker. To close this, commit a `uv.lock` (via `uv lock`) that pins every runtime and transitive dependency to an exact version, and make **both** install paths consume it via `uv sync --frozen` (Docker copies `uv.lock` into the image before syncing) rather than re-resolving ranges. `uv.lock` is committed to git (not ignored) and regenerated deliberately via `uv lock`. **Alternative considered:** rely on Docker layer caching / a hand-maintained `requirements.txt` — rejected: caching is not a contract and a hand-edited pin list drifts from `pyproject.toml`. **Alternative considered:** pin exact versions directly in `pyproject.toml` — rejected: it conflates "intent" with "resolved graph" and doesn't capture transitive deps or hashes.

### Decision: Docker installs the package **editable** so code edits need no rebuild after the first build
Base image moves `python:3.11-slim` → `python:3.13-slim`. The Dockerfile copies `pyproject.toml` + `uv.lock` + the package and runs `uv sync --frozen` into `/app/.venv` (replacing `pip install -r requirements.txt` + `COPY app.py`), then `CMD ["uv", "run", "--frozen", "onvif-sua"]` (equivalently, put `/app/.venv/bin` on `PATH` and use `CMD ["onvif-sua"]`).

The no-rebuild dev loop is an explicit requirement, not a "MAY": because `uv sync` installs the project **editable**, the interpreter resolves `import onvif_sua` to `/app/onvif_sua` (the editable target), and `docker-compose.yml` bind-mounts the host source there (`./onvif_sua:/app/onvif_sua:ro`). So after the **first** image build, editing host code and running `docker compose restart` picks up the change with **no rebuild** — the running package is the bind-mounted source, not a frozen site-packages copy. This is what makes the earlier "installed editable, or the mount shadows the copy" ambiguity concrete: it is editable, deliberately. Two constraints make it hold:
- The compose file mounts **only** `./onvif_sua`, `settings.yaml`, and `./data` — it MUST NOT mount over `/app` wholesale, or it would hide `/app/.venv` (the interpreter) and `/app/pyproject.toml` (the editable-install metadata) and break startup.
- Because templates/static resolve from the package location (RM1) and the editable target is `/app/onvif_sua`, edits to `web/templates/*` and `web/static/*` on the host are served after a restart too — the same no-rebuild path covers the polling-constant edits in `index.js`.

`settings.yaml` and `./data` mounts and all env vars stay the same. Dependency edits (adding a package / changing a pin) still require `uv lock` + an image rebuild, because deps live in `/app/.venv` inside the image, not in the mounted source; only *code* edits are rebuild-free. **Alternative considered:** a non-editable `pip install .`/`uv pip install .` into site-packages + `COPY app.py` — rejected because the bind-mount would not shadow the site-packages copy, so code edits would silently require a rebuild (the exact failure this decision removes). **Alternative considered:** mount `./app.py` and run `python -m onvif_sua` without installing — rejected because then Docker and native paths diverge; the shared `uv sync --frozen` editable install keeps both modes identical.

### Decision: `Taskfile.yml` (go-task) is the single command surface for both modes
Add a `Taskfile.yml` at the repo root that wraps the raw uv/docker commands so an operator uses one verb set regardless of mode. Planned tasks:
- Native (uv): `setup` (`uv venv --python 3.13` + `uv sync --frozen` — the same lock-frozen verb as everywhere else, NOT `uv pip install -e .`, so the Taskfile cannot re-resolve ranges behind the operator's back), `run` (`uv run onvif-sua`), `dev` (same with reload if applicable).
- Docker: `docker:build` (`docker compose build`), `docker:up` (`docker compose up -d`), `docker:down`, `docker:logs` (`docker compose logs -f`), `docker:restart` (`docker compose restart` — the edit-then-restart dev loop the bind-mount enables).
- Convenience: a default `task --list`-friendly layout; optional `clean` (remove `.venv`).

The Taskfile only shells out to the same commands documented elsewhere — it introduces no new behavior or hidden logic, so the two modes stay identical to running the commands by hand. **Alternative considered:** a `Makefile` — rejected in favor of go-task per the user's request; YAML tasks are clearer and cross-platform. **Alternative considered:** uv's `[tool.uv]` scripts only — doesn't cover the Docker path, so Taskfile is the unifying layer.

## Risks / Trade-offs

- **Circular imports between web layer and runtime state** → Put shared globals in a leaf module (`config`/`state`) imported by everyone; keep the web layer a consumer only.
- **Template extraction silently alters rendered output** (whitespace, escaping, f-string→Jinja quirks) → Diff captured renders of each page before/after extraction; only apply polling edits once parity holds.
- **MQTT payload drift during the move** → Move `_mqtt_*` functions unchanged; verify deterministically by driving discovery+state for one fixed camera through a stub `mqtt.Client` that records every `.publish(topic, payload, qos, retain)` call (no live broker), and diffing the recorded call list before vs. after — unique_ids, topics, and payloads must be byte-identical. The recorded baseline is committed as a fixture (task 1.1).
- **Deploy breakage from the mount/entrypoint change** → Ship the package-mount + `uv run onvif-sua` entrypoint change together with the code; verify the container starts and serves the dashboard before archiving. Rollback = revert the compose/Dockerfile + restore `app.py` from git.
- **Code edits silently ignored in Docker (rebuild expected)** → Install the project **editable** via `uv sync --frozen` and bind-mount `./onvif_sua:/app/onvif_sua:ro` (never mount over `/app`, which would hide `/app/.venv` and the editable-install metadata). Verify by editing a source file, running `docker compose restart` (no rebuild), and confirming the change is served. Dependency changes still need `uv lock` + rebuild — code changes do not.
- **Templates/static unresolved under a non-editable install** → Resolve directories from the package location (not CWD) and ship them as package data; verify with a plain `uv pip install .` (no bind mount) launched from an unrelated working directory.
- **Login page unstyled if `/static` is auth-gated** → Leave the `/static` mount ungated by the `_valid_session` check (it is unauthenticated by default); verify an unauthenticated request for the login stylesheet returns 200, not a 302 to `/login`.
- **Stale cached assets on long-running kiosks** → Version asset URLs (`?v=<build>`) or rely on documented `Last-Modified`/`ETag` revalidation so future polling-constant edits actually reach the panel.
- **Slower dashboard feels laggy to an operator watching the web UI** → Accepted: alarms reach Home Assistant over MQTT regardless; the visibility handler gives an instant refresh on focus, so the perceived staleness only exists on an actively-watched tab between ticks.
- **Native and Docker resolve different dependency versions** (ranges re-resolved at different build times) → Commit `uv.lock` and install both modes from it with `uv sync --frozen`, so the resolved graph is identical regardless of when each was built; verify by comparing `uv pip freeze` in the venv vs. the container.

## Migration Plan

1. Introduce the `onvif_sua/` package alongside `app.py`, moving code module by module; keep the app runnable throughout.
2. Add `pyproject.toml` with dependency ranges + console script; run `uv lock` and commit the lockfile; verify install-from-lock then `onvif-sua` and `python -m onvif_sua` both boot.
3. Extract templates/static and confirm render parity.
4. Apply the two polling changes.
5. Switch `Dockerfile` to `python:3.13-slim` + `uv sync --frozen` (editable) + `CMD ["uv", "run", "--frozen", "onvif-sua"]`, and `docker-compose.yml` to the directory mount; confirm a code edit + `docker compose restart` is served with no rebuild.
6. Verify both run modes: native install and container boot; MQTT discovery/state and the dashboard.
7. Remove `app.py`.
- **Rollback:** `git revert` the change; restore the `./app.py` mount and `python app.py` entrypoint.
