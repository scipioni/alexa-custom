## MODIFIED Requirements

### Requirement: Proactive PipeWire state enforcement
The system SHALL run a background daemon thread that monitors PipeWire events and ensures that the configured audio hardware is correctly initialized and routed. The target audio card name SHALL be sourced from `config.audio_card_name` (default `"NewPie"`) rather than being hardcoded. A `configure(cfg)` function SHALL be provided to update the module-level audio parameters after each config load or hot-reload, AND it SHALL be invoked by the config-reload path so that the values take effect at runtime. The `configure(cfg)` function SHALL be the single source of truth for module-level audio state; callers SHALL NOT bypass it by mutating module globals directly.

#### Scenario: Device profile enforced on connect
- **WHEN** a configured Bluetooth device connects in A2DP mode
- **THEN** the system automatically switches it to the `headset-head-unit` (mSBC) profile to enable the microphone

#### Scenario: Default routing snatched back
- **WHEN** another audio device (e.g., HDMI) becomes the default PipeWire sink while the configured device is connected
- **THEN** the system automatically snatches back the default status for the configured device

#### Scenario: Custom audio_card_name used for device search
- **WHEN** `config.yaml` sets `audio_card_name: ConferenceCam` and `audio.configure(cfg)` is called
- **THEN** `find_alexa_card()` matches cards containing `conferencecam` (case-insensitive) instead of `newpie`

#### Scenario: config hot-reload updates audio parameters
- **WHEN** the user edits `config.yaml` to change `output_volume` or `input_gain` and the config manager hot-reloads the file
- **THEN** `audio_hw.configure(new_config)` is invoked, the module-level globals are updated, and the AudioWatcher's next enforce cycle re-applies the new values to the hardware

### Requirement: Portable hardware mixer restore
The system SHALL provide a function to restore the NewPie's ALSA `PCM` mixer to 100% after operations that may trigger an ALSA chain re-initialisation. The function SHALL resolve the NewPie ALSA card index dynamically at call time (rather than hardcoding card 0) and SHALL be a no-op when no NewPie card is present in `/proc/asound`. This SHALL be safe to call on development hosts where the NewPie is not the system default audio device.

#### Scenario: PCM restored on Uno Q
- **WHEN** `_restore_hw_pcm()` is called while a NewPie is connected to the Arduino Uno Q
- **THEN** the NewPie's `PCM` mixer is set to 100% via `amixer -c <newpie_card_index> sset PCM 100%`

#### Scenario: no-op on Arch dev without NewPie
- **WHEN** `_restore_hw_pcm()` is called on a development host with no NewPie connected
- **THEN** the function returns without invoking `amixer` and without affecting the host's audio configuration

## ADDED Requirements

### Requirement: Runtime output volume control
The system SHALL apply `config.audio.output_volume` to all audio generated by the daemon (TTS, wake/timeout beeps, recorded-audio playback) via digital scaling of the audio data. The system SHALL NOT invoke `wpctl set-volume` to drive the system mixer, and SHALL NOT pass `--volume=` to `pw-play`. The digital scaling SHALL be the single source of output-volume attenuation. A value of `0.0` SHALL produce silence; a value of `1.0` SHALL produce unmodified loudness.

#### Scenario: Low output volume is audibly quieter
- **WHEN** `config.audio.output_volume` is set to `0.3` and the daemon plays a TTS line
- **THEN** the audio is scaled to approximately 30% of full-scale in the digital domain before being sent to PipeWire

#### Scenario: Output volume change takes effect after hot-reload
- **WHEN** the user edits `config.yaml` to change `output_volume` from `0.3` to `0.7` while the daemon is running
- **THEN** the next TTS line played after the hot-reload is scaled to 70% in the digital domain

### Requirement: Runtime input gain control (hardware-first, software fallback)
The system SHALL apply `config.audio.input_gain` to the NewPie's PipeWire source volume via `pactl set-source-volume` as the primary mechanism. The NewPie PipeWire source SHALL be resolved by name from `config.audio.input_device` at the time of each call (not cached). If the source cannot be located, the system SHALL fall back to software scaling of the captured s16le PCM in the STT capture pipeline. A value of `0.0` SHALL be clamped to `0.0` (no negative gain).

#### Scenario: Input gain changes NewPie source volume
- **WHEN** `config.audio.input_gain` is set to `1.5` and the daemon applies it
- **THEN** `pactl set-source-volume` is invoked on the resolved NewPie source with `150%`, and the NewPie's hardware mic preamp reflects the new level

#### Scenario: Input gain hot-reload takes effect
- **WHEN** the user edits `config.yaml` to change `input_gain` from `1.0` to `2.0` while the daemon is running
- **THEN** the next call to `set_input_gain()` (triggered by the config-reload callback or the AudioWatcher's enforce cycle) re-applies the new value to the hardware

#### Scenario: Fallback when source not found
- **WHEN** `set_input_gain()` is invoked and the NewPie PipeWire source cannot be located (device unplugged, name change)
- **THEN** the function logs a warning, does NOT call `pactl`, and updates the software-fallback value used by the STT capture pipeline

#### Scenario: Negative gain clamped
- **WHEN** `set_input_gain(-0.5)` is called
- **THEN** the stored value is clamped to `0.0` and a warning is logged
